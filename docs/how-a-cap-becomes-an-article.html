③ 分阶段说明

01 选题：CAP 怎么进

选题从开发者正在做的购买或集成决策出发，两层过滤：

  • 原子性：一个 CAP 只测一种机器接口能力，不把多个金融任务混成总分
  • 可评测性：存在客观输入、业务字段规则、负向控制和至少一条可授权执行路径

选题时先查 QVeris 存量 guide；相同搜索意图优先刷新已有文章，不制造互相竞争的重复页面。

02 出题：题目是契约的实例

CAP Pack 文件负责什么
cap.yaml业务边界、市场、资产类型与明确排除项
cases.yaml固定输入、正向用例、边界与负向控制
observation-schema.yaml可观察字段及其业务语义
outcome-rules.yaml怎样从观察事实得到单元结果

CAP-specific 字段留在版本化 CAP Pack；Core 只负责通用的 suite、运行、证据和 release 合约。

03 选供应商：谁进短名单

  1. Provider 与 Access Path 是两层身份，Native、Native MCP、QVeris 结果不合并
  2. 每条路径必须有官方接口来源、稳定 ID 和执行授权
  3. Direct Test 要真跑；缺凭证是尚未形成证据，不是 N/A 或低分
  4. 同一 Provider 可以有多条路径，但每条路径保留独立 run key 与结果
  5. 没有满足发布门槛的证据就延后文章结论，不用供应商声明补齐

04 定维度：通用算子 × 契约实例化

算子测什么由谁实例化
required_field_presence完整度CAP observation schema
field_type_validity准确度CAP field type / enum
row_key_completeness数据形态CAP output cardinality + row key
timestamp_freshness时效时间语义字段
market_routing市场适用性CAP case 与 Access Path applicability
language_mapping语言覆盖语言字段（有意义才测）
latency / reliability / cost网关表现执行 trace + billing
parameter_clarity参数清晰度CAP-owned Agent-interface case
single_tool_completion单工具完成恰好一个 canonical tool 的受限 Agent Trial

05 Direct Test：自己判合格

  • 固定用例：正向（真实标的检索）+ 负向（无效代码控制）
  • 每个适用单元至少 3 轮，经明确的 Native、Native MCP 或 QVeris Access Path 真实执行
  • 正向判定：契约必填字段全部返回且非空 → 过
  • 负向判定：返回空态或明确报错、不编造事件行 → 过
  • 认证、网络和 runner 故障是基础设施失败，不能伪装成 N/A 或供应商失败
  • 延迟与费用保留 Access Path 口径；QVeris 网关观测不能冒充 Native API 指标

06 Agent-interface observations：维度分开

只有 CAP 已定义测量且 release 携带证据时，才展示 Agent-interface observations：

  • 入参落参：只调 canonical 工具、必填齐全、类型合法、不幻觉多余参数、语义正确
  • 出参解读：给冻结的真实响应，AI 读出金额/日期/单位是否正确、不添油加醋、负向不编造

参数清晰度、schema 稳定性、错误恢复、分页、语言映射与单工具完成保持独立，禁止压成一个评级。

07 判定与证据

状态含义示例
Qualified全部适用规则与负向控制满足门槛只对当前 CAP 与 Access Path 成立
Not qualified至少一个适用单元未满足公开规则必须写明直接失败原因
Evidence insufficient没有可发布证据不能从文档或其他路径推断
N/A用例对该路径不适用不算通过或失败

原始证据默认私有；仓库只提交通过脱敏、披露与来源许可检查的公开证据。

08 写文章

固定结构：直接回答 → Access Path 对比表 → release 方法与证据锚点 → 逐路径事实 → 复测 → 局限 → 供应商加入与 Result challenge。

证据分级允许的说法
实测带日期、固定输入、连接器口径："2026-08-09 经 QVeris 网关实测"
官方来源供应商文档声明，带直接链接
编辑解读时间限定的买方建议："本次测试最佳适配"

09 画图

图表从 immutable release 计算生成，不是手画：render_cap_guide_charts.py 读取 release.json，输出 PNG 并把完整输入 digest 写入 charts-manifest.json：

  • 每条 Access Path 的正向字段门槛完成轮次
  • 每条 Access Path 的负向控制完成轮次
  • 图、manifest 与 release digest 一一绑定

换数据重跑即可复现，图片与证据绑定。

10 发布与复测

  • 发布前：全部链接实测 200（官网 / provider 页 / 官方文档）、manifest 完整、正文无内部信息
  • 复测：同一冻结 suite 对每个适用单元至少 3 轮；新事实生成 successor release
  • 更正：用 release digest、Access Path 和反证提交 Result challenge，历史字节不改写

④ 用分红 CAP 串一遍

  1. 选题：Dividend Events，只测有日期的每股现金分红事件；刷新已有分红 guide
  2. 出题：AAPL 分红历史检索（正向）+ 无效代码控制（负向）
  3. 选供应商：EODHD / Twelve Data / Alpha Vantage / Massive / 恒生聚源 / iFinD；FMP、Yahoo 无 canonical 工具 → 未测
  4. Direct Test：36 个适用单元全部形成终态；五条 QVeris 路径满足本 CAP，iFind Native MCP 正向三轮缺除权除息日
  5. Release：dividend-events-2026-q3-v1 绑定 54 个计划单元、36 份公开证据与 suite fingerprint
  6. Replay：用外部 digest 核对不可变发布身份，不调用供应商
  7. 画图：Direct outcome 图从 release 生成并记录完整 digest
  8. 文章：docs/guides/best-dividend-apis.md + manifest

⑤ 红线

  • 任何外部快照只作候选与来源线索，发布结论必须来自本项目 Direct Test 与 immutable release
  • 正文不暴露 CAP ID、不暴露 grade、不合成总分、不写"永久最优"
  • 缺执行授权或证据 = Evidence insufficient；只有业务不适用才是 N/A
  • 图表必须从绑定证据生成，禁止手填数值
  • 发现快照异常 → 提 issue 跟进，但不阻塞发布
